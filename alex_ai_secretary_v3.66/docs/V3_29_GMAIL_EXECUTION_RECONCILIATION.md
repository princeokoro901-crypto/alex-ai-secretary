# v3.29 — Gmail and execution-journal reconciliation

## Purpose

Cross-reference unresolved Gmail send-ledger attempts with the durable execution journal, using only the execution ID generated by Alex's controlled execution gateway. This closes the v3.28 visibility gap without guessing which execution belongs to a legacy attempt.

## Changes

- The execution gateway can optionally pass a trusted, immutable `ExecutionContext` to explicitly registered handlers. Existing handlers retain their previous signatures unless they opt in.
- The Gmail connector opts in and persists the gateway-generated execution ID with each new send-ledger reservation.
- The Gmail send ledger migrates existing SQLite databases by adding a nullable `execution_id` column. Existing rows remain unlinked; no heuristic matching is attempted.
- `GET /api/v1/connectors/gmail.email/reconciliation?limit=100` is administrator-only and reports linked, unlinked, missing-execution, wrong-action-type, and status-mismatch cases. It is read-only and emits an audit event with counts only.
- `POST /api/v1/connectors/gmail.email/uncertain-sends/{attempt_id}/reconcile` records an administrator's append-only reconciliation decision against the exact linked uncertain execution. Confirmed outcomes require an external evidence reference. The reason is limited to 500 characters and evidence reference to 200 characters.
- The new workflow never updates the Gmail ledger status, changes the execution status, retries an email, or authorizes a retry. The existing send key remains blocked even after a decision is recorded.

## Safe-use rules

- Use the provider's own message search/history or administrative evidence to investigate an uncertain send. The reconciliation API does not query Gmail and cannot independently prove delivery.
- Record a concise explanation and a reference to provider-side evidence; do not paste message bodies or OAuth secrets into reconciliation notes.
- `unlinked` legacy attempts require manual investigation. Alex must not infer a match based on timestamps, message hashes, or similar metadata.
- The execution journal and send ledger must both be persistent for the live Gmail configuration. Real Gmail sending remains disabled by default and was not exercised by these tests.

## Validation

Automated tests cover gateway-context propagation, exact execution-ID correlation, old-ledger migration, unlinked legacy rows, wrong action types, evidence-reference validation, append-only decisions, and the invariant that reconciliation never changes ledger/execution status or triggers another send. Tests use fake Google transports; no live Google credentials or external requests are used.
