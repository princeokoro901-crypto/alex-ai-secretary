# Alex v3.39 — Persistent Task Recovery

## Problem addressed

Previously, orchestration results were persisted after runtime completion. A process interruption after the runtime started but before the result was saved could leave only a start audit event, with no durable task record or idempotency mapping. A caller who lost the response could then submit the same task again under a new key.

## Behavior added

- A run is written with status `running` and recovery state `execution_pending` before the agent runtime is invoked.
- The request idempotency key is persisted in the same state-store save as that run.
- The persisted request summary contains objective, task type, required tools, selected tool, budget, mission ID, candidate-agent IDs, verification setting, input key names, and a SHA-256 digest of canonicalized input JSON. Raw input values are not copied into this summary. Existing runtime result data may still contain information generated by the runtime, so the state store must be protected.
- On startup, any durable record still marked `running` is changed to `uncertain`, receives `interrupted_after_restart` recovery state, and is persisted. When audit logging is enabled, Alex records `orchestration_interrupted`.
- If the runtime raises after invocation begins, Alex records an uncertain result and pauses a still-running mission. It does not claim the action definitely failed, and it does not retry.
- A repeated request with the same idempotency key returns the stored result, including an uncertain result, without invoking the runtime again. Reusing a key with different request metadata is rejected. The dashboard reuses the same key while the form payload remains unchanged in the current page session, and shows recovery state in history cards.
- Lifecycle reconciliation treats an interruption audit event as a terminal record for the purpose of matching state and audit history.

## Important limits

- This is only durable when `ALEX_ORCHESTRATION_STATE_PATH` is configured (and for SQLite, `ALEX_ORCHESTRATION_STATE_BACKEND=sqlite` with a path). The default in-memory configuration cannot recover across restarts.
- Mission state, runtime task/result maps, and workforce status are not made durable by this change. A recovered orchestration is diagnostic evidence, not proof of the external or simulated operation's final outcome.
- Idempotency protects only callers that reuse the same key. It is not a substitute for provider-level idempotency or execution-journal reconciliation for consequential external operations.
- There is no automatic retry, no external provider call added, and no new approval bypass. An operator must inspect an uncertain record before deciding on any further action.
- Browser automation and live integrations were not part of this source-level milestone.

## Validation

The release validation record is `TEST_RESULTS.txt`. Focused tests cover JSON and SQLite restart recovery, runtime exceptions, pre-runtime persistence, idempotency replay, omission of raw input values from recovery metadata, and lifecycle reconciliation.
